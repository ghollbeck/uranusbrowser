# Meeting notes

UrAnus Browser can record a meeting you are in, show a live transcript, and write grounded notes when you stop. It lives in the Agent panel (the microphone button in its header). It only ever starts from the **Start recording** button, on the tab you are looking at, and shows a recording bar for as long as it runs.

This is the user's own meetings. It does not join meetings or speak in them, and nothing records on a schedule: calendar reminders and the meeting-tab offer (below) only lead to the same Start button.

## What it does

1. **Start** (panel, a click): the background opens a hidden *offscreen document* (`shell/ui/meetingsCapture.ts`) that records the microphone ("Me") through one `AudioContext`. The meeting tab's sound ("Others") is added through the same `AudioContext` once the user right-clicks the page or presses the shortcut (see below).
2. Audio is cut into ~10 s chunks of 16 kHz mono WAV (`shell/lib/meetingsChunker.ts`), silent chunks are dropped, and each chunk is sent to the **native host**, which sends it to an engine and returns text. The host keeps no audio.
3. Text lines appear in the panel within a few seconds. Where the page is Google Meet, Zoom (web) or Teams (web), the "Others" lines are named from the highlighted speaker tile.
4. **Stop** (always works; it never waits on the host): the transcript is saved, and the notes are written. For the OpenAI engine the model only returns the *numbers* of transcript lines (overview, decisions, action items, open questions); the notes quote those original lines with speaker and time. A line that tells the model what to do is just a line.
5. The meeting is saved in this profile (`chrome.storage.local`, `unlimitedStorage`). From the meeting view: rename, Copy as Markdown, Discuss in chat (sends the notes to the agent as your own message, fenced as untrusted data), Delete. The list has Delete all.

## Where audio and text go

| | Engine "OpenAI" | Engine "On this Mac" |
| --- | --- | --- |
| Audio | to OpenAI's `audio/transcriptions` endpoint, one chunk per request, with the Keychain key | to a `whisper-server` on `127.0.0.1` (already installed; never downloaded) |
| Transcript text | stored here; sent to OpenAI again only to write the notes | stored here; the notes are a no-model digest unless you press "Write notes with OpenAI" |
| Model | `ANUS_MEETING_TRANSCRIBE_MODEL`, default `gpt-4o-mini-transcribe` (`gpt-4o-transcribe` and `whisper-1` also work) | the installed ggml model |

Notes use `ANUS_MEETING_SUMMARY_MODEL`, else `ANUS_AGENT_MODEL`, else the chat's default.

The local engine is used only if a `whisper-server` binary and a ggml model are *already there*: `ANUS_WHISPER_SERVER` / `ANUS_WHISPER_MODEL` (set `ANUS_WHISPER_SERVER=off` to disable), or, failing that, where the user's OpenWhisper app keeps them (`/Applications/OpenWhisper.app/Contents/Resources/bin/whisper-server`, `~/Library/Application Support/OpenWhisper/whisper-models/ggml-{small,base}.bin`). UrAnus Browser checks the files exist and never creates, downloads or installs one.

Transcript text is never logged, never put in a URL, and only rendered as DOM text. The API key stays in the native host.

## What Chromium allows here (found by trying it)

These were checked in this UrAnus Browser build (Chromium 158, the shell as a component extension) with a throwaway profile.

- **`chrome.offscreen` and `chrome.tabCapture` exist** for the shell (manifest permissions `offscreen`, `tabCapture`).
- **The Agent panel's own page cannot capture media.** Its `WebContents` (patch 0042) is created by UrAnus Browser without a media-permission delegate, so `getUserMedia` there never completes. The recorder is therefore an offscreen document, which survives the panel being closed.
- **Tab capture needs an "invocation" the shell does not get from the panel.** `chrome.tabCapture.getMediaStreamId({ targetTabId })` fails with *"Extension has not been invoked for the current page (see activeTab permission)"*, even for a component extension with `<all_urls>`. Chromium only grants that per-tab permission when the user clicks one of the extension's context-menu items, uses one of its keyboard commands, or clicks its toolbar button. A click inside the Agent panel is not one of those, and the browser's own `anus-open-location` command is dispatched as a plain event (patch 0009), without the grant. Adding `tabCaptureForTab` to the manifest does not help.
  - **What the shell does (no Chromium patch):** Start begins the **microphone only** and says so. The tab's sound is added **during** the recording by one of two gestures Chromium honours, handled in `shell/lib/meetingsTabAudio.ts`:
    1. a **page context-menu item**, "UrAnus Browser: add this tab's audio to the meeting notes" (contexts page, frame, video, audio, selection). It is created when a recording starts and removed when it stops, so it exists only while recording;
    2. the extension **command** `anus-add-tab-audio`, suggested key ⌘⇧Y (Ctrl+Shift+Y elsewhere; not used by any UrAnus Browser shortcut). The panel shows the key Chromium actually assigned (`chrome.commands.getAll()`), and leaves it out if none was.
  - In either handler `getMediaStreamId` is called first, in the same turn as the click (that click is the grant), and the id goes to the capture page, which adds the tab as "Others" from that moment (`meeting:capture-attach-tab`; its chunks are placed on the recording clock). It can be added before or after the microphone starts, and replaced by another tab; a second click on the same tab changes nothing. The panel and the recording bar say plainly, while there is no tab audio: *"Remote participants' audio isn't being captured yet. Right-click the meeting page and choose 'UrAnus Browser: add this tab's audio to the meeting notes' (or press ⌘⇧Y)."* Nothing claims "Others" is recorded until the capture page confirms it, and then the card names the site.
  - A refusal ("not invoked", a page that can't be captured) is shown as a message and the recording continues with the microphone.
  - **Not automated, and unverified here:** that the native context-menu item really shows up on web pages in UrAnus Browser, that clicking it really gives the grant, and that ⌘⇧Y reaches the extension (UrAnus Browser routes its own shortcuts through the browser first, patch 0016). The tests cover the code both gestures call.
  - **Manual test (needs a real meeting tab and a microphone):** 1. Open a meeting (or any page playing audio, e.g. a YouTube video). 2. Agent panel, microphone button, Start recording; allow the microphone if asked. 3. The card shows the "Remote participants' audio isn't being captured yet" how-to. 4. Right-click the page, choose "UrAnus Browser: add this tab's audio to the meeting notes" (or press ⌘⇧Y with the page in front). 5. The card changes to "<site>: the microphone and the tab's sound are being turned into text", an "Others" meter appears, and the tab keeps playing out loud. 6. Stop, open the meeting: "Others" lines are there, named if the page is Meet, Zoom or Teams. 7. Also try clicking the item twice (nothing changes) and right-clicking a different tab. If the item or the key does nothing, a Chromium patch (a `anusPrivate` method that grants the tab) is the fallback.
- **The microphone prompt cannot be shown for an offscreen document.** If the extension origin has no microphone permission yet, Start fails after a few seconds with "UrAnus Browser may need your permission first" and offers **Allow the microphone…**, which opens `meetingsCapture.html?permission=1` in a normal tab: that page calls `getUserMedia`, so Chromium can show its prompt, and the grant is remembered for the extension. The user then presses Start again.
- **macOS microphone access for the app itself.** The installed `UrAnus Browser.app` is ad-hoc signed and its `Info.plist` has **no `NSMicrophoneUsageDescription`**. macOS refuses (or ends the process) when an app asks for the microphone without one, so the release packaging must add it (and `com.apple.security.device.audio-input` if the app is ever signed with the hardened runtime). This was not exercised here: no real microphone was used.
- **Autoplay:** an offscreen document's `AudioContext` may start suspended. With a live microphone it runs; in the test (which uses recorded speech) the browser is launched with `--autoplay-policy=no-user-gesture-required`. The capture page refuses to record if the audio engine is not running.
- **Tab capture mutes the tab for the user unless it is played again.** The recorder routes the captured tab stream to the speakers as well as to the tap, so the meeting stays audible.
- **Echo:** the microphone is opened with echo cancellation on, and Chromium's canceller listens to what the same browser plays (including the recorder's own playback of the tab). As a second layer, `cleanMeetingTranscript` removes whole sentences of 7+ words that the microphone line repeats exactly from the "Others" line at the same time (ported from OpenWhisper).

## Calendar reminders and the meeting-tab offer

Built to remind the user the way Strawberry does, without OAuth: the calendar is read from its private iCal (ICS) address.

- **Pure logic** (`shared/calendar.ts`, tests in `tests/calendar.test.ts`): the address check (https; `webcal://` becomes https; no credentials; shown as `host…`), RFC 5545 unfolding and property parsing, VEVENTs with DTSTART/DTEND/DURATION, SUMMARY, LOCATION, DESCRIPTION, URL, UID, STATUS:CANCELLED, all-day events (kept out of prompts), UTC, floating (local) and `TZID=` times converted with `Intl.DateTimeFormat` (no zone library; common Outlook Windows zone names are mapped; an unknown zone is read as local time). RRULE FREQ=DAILY/WEEKLY/MONTHLY/YEARLY with INTERVAL, COUNT, UNTIL, BYDAY (ordinals for MONTHLY), BYMONTHDAY, BYSETPOS and WKST; EXDATE; RECURRENCE-ID overrides that move or cancel one occurrence. Only now−1 h … now+36 h is expanded; a series without COUNT jumps straight to the window, and every rule stops after 5,000 periods. Rules with BYMONTH, BYWEEKNO, BYYEARDAY or BYHOUR/MINUTE/SECOND aren't expanded (the event counts once, at its start), so they can't produce wrong prompts.
- **Meeting links**: X-GOOGLE-CONFERENCE / X-MICROSOFT-SKYPETEAMSMEETINGURL, then URL, LOCATION, DESCRIPTION, through joinly's `checkMeetingUrl` (https, the platform's own host as a whole name, no credentials or port) plus a meeting path: a Meet code, Zoom `/j/` or `/my/`, Teams `/l/meetup-join/` or `/meet/`.
- **Background** (`shell/calendar.ts`, state in `shell/lib/calendarState.ts`): `fetch` with `credentials: 'omit'`, `cache: 'no-store'`, a 20 s timeout and a 15 MB cap; an error message never contains the address, and failures are logged without it. Reads on start (if the cached read is over 5 minutes old), on the `calendar-refresh` alarm every 10 minutes, and on demand. The meetings with a link in the window are cached (`calendar:cache`: id, cleaned title, start, end, platform, link) so an alarm can prompt without fetching; the address is under `calendar:url`; marks (`calendar:marks`) remember, per occurrence id (UID + start, hashed) and per meeting tab, what was dismissed or notified. A one-shot `calendar-prompt` alarm wakes the background for the next prompt.
- **Notification** (`chrome.notifications`, manifest permission `notifications`): "*title* starts in 2 min", from 2 minutes before to 10 minutes after the start, once per occurrence. A click on it opens the meeting only; buttons **Join & record** and, when joinly is switched on (`joinly.available()`), **Record + AI assistant** (else **Dismiss**). The reminder's id carries `+assistant` when it has that button. The listeners are added in the background's first turn (`listenCalendar`), so a click wakes it.
- **Open & record** opens the link with the shell's own tab path (`openTab`, window focused), opens the Agent panel (`agentPanel:get` / `agentPanel:toggle`), and broadcasts `calendar:focus` (also returned by `calendar:get` for a minute, for a panel that is just loading). Then it **starts the notes itself** (`meetings.startFor(host)`: waits up to 8 s for the meeting's tab to be in front, then the same `start()` as Start recording) and posts "Recording *title*" with **Stop recording** (`meetings.stopNow()`). The click on the notification or the panel is the go-ahead. The microphone starts at once; the meeting tab's own audio still needs ⇧⌘Y (tab capture needs an invocation of the extension, which a notification click isn't). If `start()` fails it broadcasts `calendar:focus` and the Meetings sheet shows **Ready to record this meeting**. **Record + AI assistant** also calls `joinly.joinFor(url)`, the sheet's checks (switched on, accepted host, one meeting at a time) with the user's click as the confirmation; a failure gets a notification of its own.
- **Panel** (`ui/meetingsCalendar.ts`): the Calendar screen (address, Test / Save / Remove, Check now, "Offer to record meetings"), the Upcoming card (next 3 meetings today), and `#meeting-strip` above the conversation: a meeting starting within 5 minutes, or, when the active tab's address is a live meeting (`liveMeetingTab`) and nothing records, "Record this meeting?". Nothing is injected into pages; only the tab's address is read.
- **Untrusted text**: event titles are flattened to one line without control or bidi characters, clipped to 120 characters, drawn as DOM text, and never put into the conversation or the meeting's title (so "Discuss in chat" never carries them). Descriptions are only searched for a link and are not kept. The address and events are never sent to the model.
- **Not verified without launching the app:** that `chrome.notifications` shows on macOS in this Chromium build (the app may need notification permission in System Settings), that a click on the notification wakes the background and opens the panel, and how Google, Outlook and iCloud serve their ICS files to the extension's `fetch`. The parser, expansion, links, prompts and stored state are unit-tested.

## What can end a recording

The Stop button; closing the meeting tab; the native helper stopping; the capture page failing; the hard limit of 3 hours (enforced in the capture page *and* in the background). Closing the panel while recording asks: Stop and close, Keep recording, Cancel.

## Speaker names

While recording, once a second, the background runs `chrome.scripting.executeScript` in the meeting tab (isolated world, no content script, nothing added to the page, nothing clicked) with `readMeetingPage` (`shell/lib/meetingsDom.ts`). Selectors come from joinly's platform controllers (MIT): Meet `div[data-participant-id]` tiles, Zoom `speaker-active-container…` frames, Teams `stage-layout` menu items. It fails soft: no match means the lines stay "Others". The timeline is merged into the transcript by overlap, as joinly does: the speaker with the most highlighted time inside the line (plus 0.6 s of slack, because the highlight lags) wins, if they hold at least half of the named time and a real share of the line. A 10-second chunk can contain two speakers; it is then labelled with whoever spoke most. Self-introductions ("I'm Alice") are only ever offered as a suggestion in the meeting view.

## Tests

- Unit: `tests/calendar.test.ts` (address check, unfolding, zones, all-day/cancelled, recurrence with EXDATE and overrides, the step cap, meeting links and look-alikes, live meeting tabs, prompt timing, stored state), `tests/meetingsTabAudio.test.ts` (fake `chrome.contextMenus`/`commands`/`tabCapture`: the menu exists only while recording and is removed on stop, the click calls `getMediaStreamId` in the same turn, a repeat is a no-op, another tab replaces, a refusal gives a clear message), `tests/meetings.test.ts` (ported OpenWhisper cases, grounded summary, name merge, WAV), `tests/meetingHost.test.ts` (host engines with a fake fetch and a fake whisper server, scrubbing, limits, prompt-injection and retraction cases), `tests/meetingsState.test.ts` (chunker, storage).
- End to end: `node chromium/tests/e2e-meetings.mjs --shell-dir chromium/shell/dist` drives the real panel. It uses recorded speech (made with `say`) in place of the microphone, and, through the same code the menu item and shortcut call (`meetings:testGesture`, test mode only), in place of the tab, because a real microphone prompt and Chromium's tab-capture invocation can't be automated; everything after the audio source is the real path, including the real OpenAI endpoints (a few cheap calls) through this worktree's built host.  It needs the OpenAI key in the Keychain.
